SQL Interview Cheat Sheet

Mid-Level Focus — Window Functions, CTEs, Joins, Optimization & Scenario Questions

1 JOIN Types — Visual Guide

INNER JOIN

Only matching rows from both tables.

SELECT a.id, b.name FROM orders a INNER JOIN customers b ON a.cust_id = b.id;
most common

LEFT JOIN

All rows from left table + matches from right. NULLs where no match.

SELECT a.id, b.name FROM orders a LEFT JOIN customers b ON a.cust_id = b.id;
keeps all left rows

RIGHT JOIN

All rows from right table + matches from left. Rarely used — just flip the LEFT JOIN.

SELECT a.id, b.name FROM customers b RIGHT JOIN orders a ON a.cust_id = b.id;
avoid — use LEFT instead

FULL OUTER JOIN

All rows from both tables. NULLs on both sides where no match.

SELECT a.id, b.id FROM table_a a FULL OUTER JOIN table_b b ON a.key = b.key;
reconciliation / gap analysis

CROSS JOIN

Cartesian product — every row × every row. No ON clause.

SELECT a.size, b.color FROM sizes a CROSS JOIN colors b;
row explosion — use carefully

SELF JOIN

Table joined to itself. Common for hierarchies (employee → manager).

SELECT e.name AS employee, m.name AS manager FROM employees e LEFT JOIN employees m ON e.manager_id = m.id;
hierarchy queries

2 JOIN Traps & Edge Cases

Trap 1: Duplicate rows from one-to-many JOINs

If orders has 1 row and order_items has 5 rows for that order, INNER JOIN produces 5 rows — not 1. Aggregates (SUM, COUNT) on the orders side will be inflated.

-- Wrong: SUM(order_total) is 5x the real value SELECT o.id, SUM(o.total) FROM orders o JOIN order_items i ON o.id = i.order_id GROUP BY o.id; -- Fix 1: Aggregate before joining SELECT o.id, o.total, sub.item_count FROM orders o JOIN ( SELECT order_id, COUNT(*) AS item_count FROM order_items GROUP BY order_id ) sub ON o.id = sub.order_id; -- Fix 2: Use DISTINCT in aggregation SELECT o.id, MAX(o.total), COUNT(i.id) FROM orders o JOIN order_items i ON o.id = i.order_id GROUP BY o.id;

Trap 2: NULLs in JOIN keys

NULL = NULL evaluates to FALSE in SQL. Rows with NULL keys will never match in any JOIN. They silently disappear from INNER JOINs and appear as NULLs in LEFT JOINs.

Trap 3: Accidental CROSS JOIN

Forgetting the ON clause or using a comma-separated FROM with no WHERE produces a cartesian product. 10K × 10K = 100M rows.

-- This is a CROSS JOIN (no join condition): SELECT * FROM orders, customers; -- Always use explicit JOIN syntax.

Anti-Join Pattern: Find rows with NO match

Customers who have never ordered:

-- Method 1: LEFT JOIN + IS NULL (most readable) SELECT c.id FROM customers c LEFT JOIN orders o ON c.id = o.cust_id WHERE o.id IS NULL; -- Method 2: NOT EXISTS (often fastest) SELECT c.id FROM customers c WHERE NOT EXISTS ( SELECT 1 FROM orders o WHERE o.cust_id = c.id ); -- Method 3: NOT IN (careful with NULLs!) SELECT c.id FROM customers c WHERE c.id NOT IN ( SELECT cust_id FROM orders WHERE cust_id IS NOT NULL -- critical! );

3 UNION vs UNION ALL vs INTERSECT

UNION

Combines results, removes duplicates. Slower — requires sort/distinct step.

SELECT city FROM customers UNION SELECT city FROM suppliers;
deduplication overhead

UNION ALL

Combines results, keeps duplicates. Faster — no dedup step.

SELECT city FROM customers UNION ALL SELECT city FROM suppliers;
prefer this when dupes are ok

INTERSECT

Only rows that appear in BOTH result sets.

SELECT city FROM customers INTERSECT SELECT city FROM suppliers;
common values

EXCEPT / MINUS

Rows in first set but NOT in second. EXCEPT (ANSI) = MINUS (Oracle).

SELECT city FROM customers EXCEPT SELECT city FROM suppliers;
difference / gap finding

Rule: Column count and types must match

All queries in a UNION/INTERSECT/EXCEPT must return the same number of columns with compatible types. Column names come from the first query.

Aggregation

GROUP BY, HAVING, and the traps that catch candidates

4 GROUP BY Deep Dive

Basic Aggregation

Every non-aggregated column in SELECT must be in GROUP BY.

SELECT department, COUNT(*) AS cnt, AVG(salary) AS avg_sal FROM employees GROUP BY department;

GROUP BY Multiple Columns

Groups by the combination of all listed columns.

SELECT department, job_title, COUNT(*) AS cnt FROM employees GROUP BY department, job_title;

GROUPING SETS

Multiple grouping levels in one query. Avoids multiple UNIONs.

SELECT department, job_title, SUM(salary) FROM employees GROUP BY GROUPING SETS ( (department, job_title), (department), () -- grand total );
advanced

ROLLUP & CUBE

ROLLUP = hierarchical subtotals. CUBE = all combinations.

-- ROLLUP: dept → dept+title → grand GROUP BY ROLLUP(department, job_title) -- CUBE: every combination GROUP BY CUBE(department, job_title)
reporting subtotals

5 HAVING vs WHERE

WHERE

Filters rows before aggregation.

-- Only active employees SELECT dept, AVG(salary) FROM employees WHERE status = 'active' GROUP BY dept;

HAVING

Filters groups after aggregation.

-- Only depts with 5+ people SELECT dept, COUNT(*) FROM employees GROUP BY dept HAVING COUNT(*) >= 5;

Interview tip: "Can you use WHERE with aggregate functions?"

No. WHERE SUM(salary) > 1000 is a syntax error. Aggregates can only be filtered with HAVING. WHERE runs before GROUP BY, so aggregates don't exist yet.

6 GROUP BY Traps

Trap 1: SELECT column not in GROUP BY

MySQL allows this (picks arbitrary value). PostgreSQL, SQL Server, Snowflake reject it. Always include all non-aggregated columns in GROUP BY.

-- Fails in most databases: SELECT department, employee_name, COUNT(*) FROM employees GROUP BY department; -- employee_name is not aggregated or grouped

Trap 2: COUNT(*) vs COUNT(column)

COUNT(*) counts all rows including NULLs. COUNT(column) counts only non-NULL values. Big difference when column has NULLs.

-- 100 rows, 20 have NULL email SELECT COUNT(*), -- 100 COUNT(email), -- 80 COUNT(DISTINCT email) -- unique non-NULL FROM customers;

Trap 3: AVG ignores NULLs

Values: 10, 20, NULL. AVG = 15 (not 10). NULL rows are excluded from both numerator and denominator. If you want NULLs treated as 0, use COALESCE first.

-- Treating NULLs as 0: AVG(COALESCE(bonus, 0))

Window Functions

The #1 most-tested topic in mid-level SQL interviews

7 Core Window Functions

Anatomy of a Window Function

function_name(expression) OVER ( PARTITION BY col1, col2 -- optional: groups ORDER BY col3 -- optional: sort ROWS/RANGE BETWEEN ... -- optional: frame )

PARTITION BY = GROUP BY but without collapsing rows. ORDER BY = sort within partition. Frame = which rows the function sees.

When to use which?

  • ROW_NUMBER: Deduplication (pick 1 row per group), pagination
  • RANK: Competition-style ranking (skip positions after ties)
  • DENSE_RANK: Top-N queries where you want N distinct values, not N rows

9 Running & Moving Calculations

Running Total

SELECT order_date, amount, SUM(amount) OVER ( ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW ) AS running_total FROM orders;

Default frame when ORDER BY is present. Cumulative sum from first row to current.

3-Day Moving Average

SELECT order_date, amount, AVG(amount) OVER ( ORDER BY order_date ROWS BETWEEN 2 PRECEDING AND CURRENT ROW ) AS moving_avg_3 FROM orders;

Current row + 2 previous = 3-row window. First 2 rows average what's available.

Partition Running Total

SELECT department, order_date, amount, SUM(amount) OVER ( PARTITION BY department ORDER BY order_date ) AS dept_running_total FROM orders;

Running total resets per department.

Percent of Total

SELECT department, amount, amount * 100.0 / SUM(amount) OVER () AS pct_of_total, amount * 100.0 / SUM(amount) OVER ( PARTITION BY department ) AS pct_of_dept FROM orders;

Empty OVER() = entire result set. PARTITION BY = within group.

Frame Trap: ROWS vs RANGE

ROWS: Physical row count. RANGE: Logical value range — ties get the same frame. Default with ORDER BY is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which includes all ties. For a strict running total, always specify ROWS explicitly.

10 LEAD / LAG

LAG(col, offset, default)

Looks backward (previous rows).

-- Previous month's sales SELECT month, sales, LAG(sales, 1, 0) OVER ( ORDER BY month ) AS prev_month_sales FROM monthly_sales;

LEAD(col, offset, default)

Looks forward (next rows).

-- Next month's sales SELECT month, sales, LEAD(sales, 1, 0) OVER ( ORDER BY month ) AS next_month_sales FROM monthly_sales;

Classic Interview Pattern: Month-over-Month Growth

SELECT month, sales, LAG(sales) OVER (ORDER BY month) AS prev, ROUND( (sales - LAG(sales) OVER (ORDER BY month)) * 100.0 / NULLIF(LAG(sales) OVER (ORDER BY month), 0) , 2) AS mom_growth_pct FROM monthly_sales;

NULLIF prevents division by zero when previous month sales = 0.

11 Window Function Q&A

01 Can you use window functions in WHERE? ▼

No. Window functions execute after WHERE in the order of operations. You must wrap them in a subquery or CTE.

-- Wrong: SELECT * FROM sales WHERE ROW_NUMBER() OVER (ORDER BY amount DESC) <= 5; -- Correct: WITH ranked AS ( SELECT *, ROW_NUMBER() OVER (ORDER BY amount DESC) AS rn FROM sales ) SELECT * FROM ranked WHERE rn <= 5;
02 Difference between window function and GROUP BY? ▼

GROUP BY collapses rows — one output row per group. You lose row-level detail.

Window functions keep all rows and add the calculation as a new column. You keep row-level detail alongside the aggregate.

-- GROUP BY: 3 departments → 3 rows SELECT dept, AVG(salary) FROM emp GROUP BY dept; -- Window: all employee rows kept, avg added SELECT emp_name, dept, salary, AVG(salary) OVER (PARTITION BY dept) AS dept_avg FROM emp;
03 What is the default window frame? ▼

Depends on whether ORDER BY is present:

With ORDER BY: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — this includes all rows with the same ORDER BY value (ties). Catches people off guard with running sums.

Without ORDER BY: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING — the entire partition.

If you want a strict physical-row running total, always specify ROWS explicitly.

04 Deduplicate rows — pick latest per customer? ▼
WITH ranked AS ( SELECT *, ROW_NUMBER() OVER ( PARTITION BY customer_id ORDER BY order_date DESC ) AS rn FROM orders ) SELECT * FROM ranked WHERE rn = 1;

ROW_NUMBER guarantees exactly 1 row per customer. RANK/DENSE_RANK could return multiple if dates tie.

05 Top N per group? ▼

Top 3 highest-paid employees per department:

WITH ranked AS ( SELECT *, DENSE_RANK() OVER ( PARTITION BY department ORDER BY salary DESC ) AS dr FROM employees ) SELECT * FROM ranked WHERE dr <= 3;

DENSE_RANK ensures you get all ties at position 3 (could be more than 3 rows). Use ROW_NUMBER if you want exactly 3 rows regardless of ties.

06 FIRST_VALUE / LAST_VALUE trap? ▼

FIRST_VALUE works as expected. LAST_VALUE often returns the current row — not the actual last row. Why? Default frame is ...AND CURRENT ROW, so the "last" value is always the current row.

-- Fix: extend frame to end of partition LAST_VALUE(sales) OVER ( ORDER BY month ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING )

Subqueries & CTEs

Structuring complex queries cleanly

12 Subquery Types

Scalar Subquery

Returns a single value. Used in SELECT, WHERE, or HAVING.

SELECT name, salary, salary - (SELECT AVG(salary) FROM emp) AS diff_from_avg FROM emp;

Row Subquery

Returns a single row with multiple columns.

SELECT * FROM emp WHERE (dept, salary) = ( SELECT dept, MAX(salary) FROM emp WHERE dept = 'Sales' );

Table Subquery (Derived Table)

Returns a result set. Used in FROM — must be aliased.

SELECT d.dept, d.avg_sal FROM ( SELECT dept, AVG(salary) AS avg_sal FROM emp GROUP BY dept ) d WHERE d.avg_sal > 50000;

EXISTS Subquery

Returns TRUE/FALSE. Checks for existence — doesn't return data.

SELECT c.name FROM customers c WHERE EXISTS ( SELECT 1 FROM orders o WHERE o.cust_id = c.id AND o.amount > 1000 );
often fastest for existence checks

13 CTEs — WITH Clause

Basic CTE

WITH dept_stats AS ( SELECT department, AVG(salary) AS avg_sal, COUNT(*) AS headcount FROM employees GROUP BY department ) SELECT d.department, d.avg_sal FROM dept_stats d WHERE d.headcount >= 5;

Multiple CTEs

WITH orders_summary AS ( SELECT cust_id, SUM(amount) AS total FROM orders GROUP BY cust_id ), high_value AS ( SELECT cust_id, total FROM orders_summary WHERE total > 10000 ) SELECT c.name, h.total FROM customers c JOIN high_value h ON c.id = h.cust_id;

Recursive CTE

-- Employee hierarchy (org chart) WITH RECURSIVE org AS ( -- Anchor: top-level (no manager) SELECT id, name, manager_id, 1 AS lvl FROM employees WHERE manager_id IS NULL UNION ALL -- Recursive: each level down SELECT e.id, e.name, e.manager_id, o.lvl + 1 FROM employees e JOIN org o ON e.manager_id = o.id ) SELECT * FROM org ORDER BY lvl;
hierarchy / tree traversal

Recursive CTE: Running Sequence

-- Generate numbers 1 to 100 WITH RECURSIVE nums AS ( SELECT 1 AS n UNION ALL SELECT n + 1 FROM nums WHERE n < 100 ) SELECT n FROM nums;

Useful for generating date series, filling gaps, or testing.

14 Correlated vs Non-Correlated Subqueries

Non-Correlated

Inner query runs once. Independent of outer query.

SELECT * FROM emp WHERE salary > ( SELECT AVG(salary) FROM emp );

The subquery doesn't reference the outer query. Runs once, result reused for every outer row.

Correlated

Inner query runs once per outer row. References outer query.

SELECT * FROM emp e WHERE salary > ( SELECT AVG(salary) FROM emp WHERE dept = e.dept );

Notice e.dept — inner query depends on outer row. Runs for each employee. Slower on large tables.

Interview note: CTEs are NOT always faster

CTEs are about readability, not performance. Most engines inline the CTE into the main query — same execution plan as a subquery. If you reference a CTE multiple times and it's expensive, the engine may re-execute it each time. In that case, materialize into a temp table.

Query Execution & Optimization

How SQL actually runs — and how to make it faster

16 SQL Order of Execution

SQL does NOT execute top-to-bottom. Actual order:

1. FROM / JOIN -- identify tables, join them 2. WHERE -- filter rows 3. GROUP BY -- aggregate into groups 4. HAVING -- filter groups 5. SELECT -- evaluate expressions, aliases 6. DISTINCT -- remove duplicates 7. ORDER BY -- sort results 8. LIMIT / OFFSET -- paginate

Why this matters in interviews:

  • You can't use a SELECT alias in WHERE — WHERE runs before SELECT
  • You can use a SELECT alias in ORDER BY — ORDER BY runs after SELECT
  • You can't use window functions in WHERE — they run during SELECT
  • HAVING can use aggregate functions — GROUP BY has already run
  • LIMIT runs last — so ORDER BY + LIMIT is correct for "Top N"

17 Query Optimization

SELECT Only What You Need

  • Avoid SELECT * — forces full row reads
  • Name specific columns — helps index-only scans
  • Especially in subqueries: EXISTS (SELECT 1 ...)

Filter Early

  • Put conditions in WHERE, not HAVING
  • Filter before JOINs when possible
  • Use LIMIT during development

JOIN Optimization

  • Join on indexed columns
  • Smaller table first in joins (query planner usually handles this)
  • Avoid functions on join keys: ON UPPER(a.name) = UPPER(b.name) kills indexes

Avoid These Anti-Patterns

  • WHERE YEAR(date_col) = 2026 — wrapping column in function prevents index use
  • WHERE col LIKE '%text%' — leading wildcard = full scan
  • WHERE col != 'value' — negation often skips indexes
  • Implicit type conversions — comparing varchar to int

EXPLAIN / EXPLAIN ANALYZE

  • Read the execution plan before optimizing
  • Look for: Seq Scan (full scan), Nested Loop (slow on large sets), Sort (memory pressure)
  • EXPLAIN = plan only. EXPLAIN ANALYZE = runs query + shows actual times

Use UNION ALL over UNION

  • UNION = sort + deduplicate. Expensive.
  • UNION ALL = just concatenate. Fast.
  • Only use UNION when you specifically need deduplication

18 Indexing Essentials

What Is an Index?

A data structure (usually B-tree) that speeds up lookups. Like a book's index — jump to the page instead of scanning every page.

CREATE INDEX idx_orders_cust ON orders(customer_id);

Clustered vs Non-Clustered

Clustered: Physically reorders table data. One per table (usually the PK).
Non-Clustered: Separate structure pointing to data. Multiple allowed.

SQL Server / MySQL terminology

Composite Index

Index on multiple columns. Column order matters — follows the leftmost prefix rule.

CREATE INDEX idx_comp ON orders(customer_id, order_date); -- Uses index: WHERE customer_id = 5 WHERE customer_id = 5 AND order_date > '...' -- Does NOT use index: WHERE order_date > '...' -- skips first column

When NOT to Index

Indexes slow down writes (INSERT/UPDATE/DELETE). Don't index:

  • Low-cardinality columns (boolean, status with 3 values)
  • Tables with heavy write loads
  • Small tables (full scan is faster than index lookup)
  • Columns rarely used in WHERE/JOIN/ORDER BY

21 CASE Expressions

Simple CASE

SELECT name, CASE status WHEN 'A' THEN 'Active' WHEN 'I' THEN 'Inactive' ELSE 'Unknown' END AS status_label FROM users;

Searched CASE

SELECT name, salary, CASE WHEN salary >= 100000 THEN 'Senior' WHEN salary >= 60000 THEN 'Mid' WHEN salary >= 30000 THEN 'Junior' ELSE 'Entry' END AS band FROM employees;

Evaluated top-to-bottom. First matching WHEN wins. Order matters.

CASE in Aggregation

-- Pivot: count orders by status SELECT COUNT(CASE WHEN status = 'shipped' THEN 1 END) AS shipped, COUNT(CASE WHEN status = 'pending' THEN 1 END) AS pending, COUNT(CASE WHEN status = 'cancelled' THEN 1 END) AS cancelled FROM orders;
manual pivot

CASE in ORDER BY

-- Custom sort order SELECT * FROM tasks ORDER BY CASE priority WHEN 'critical' THEN 1 WHEN 'high' THEN 2 WHEN 'medium' THEN 3 WHEN 'low' THEN 4 ELSE 5 END;

Interview Q&A

Scenario-Based Questions & Conceptual Deep Dives

23 Scenario-Based Questions

01 Find the second highest salary ▼

Three approaches — know all three:

-- Method 1: Subquery SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees); -- Method 2: DENSE_RANK (handles ties correctly) WITH ranked AS ( SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS dr FROM employees ) SELECT DISTINCT salary FROM ranked WHERE dr = 2; -- Method 3: OFFSET (simple but fragile) SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1;

Best answer: DENSE_RANK. Handles ties, easily extends to Nth highest, works per department with PARTITION BY.

02 Find duplicate records ▼
-- Find duplicates SELECT email, COUNT(*) AS cnt FROM users GROUP BY email HAVING COUNT(*) > 1; -- Delete duplicates (keep lowest id) DELETE FROM users WHERE id NOT IN ( SELECT MIN(id) FROM users GROUP BY email ); -- Alternative with ROW_NUMBER: WITH dupes AS ( SELECT id, ROW_NUMBER() OVER ( PARTITION BY email ORDER BY id ) AS rn FROM users ) DELETE FROM users WHERE id IN ( SELECT id FROM dupes WHERE rn > 1 );
03 Find customers who ordered every month in 2025 ▼
SELECT customer_id FROM orders WHERE order_date >= '2025-01-01' AND order_date < '2026-01-01' GROUP BY customer_id HAVING COUNT(DISTINCT DATE_TRUNC('month', order_date) ) = 12;

Key insight: COUNT(DISTINCT month) = 12 ensures all 12 months have at least one order. Using DATE_TRUNC normalizes dates to month level.

04 Find consecutive login days per user ▼

Classic "gaps and islands" problem:

WITH numbered AS ( SELECT user_id, login_date, login_date - ROW_NUMBER() OVER ( PARTITION BY user_id ORDER BY login_date ) * INTERVAL '1 day' AS grp FROM ( SELECT DISTINCT user_id, login_date::date AS login_date FROM logins ) t ) SELECT user_id, MIN(login_date) AS streak_start, MAX(login_date) AS streak_end, COUNT(*) AS streak_days FROM numbered GROUP BY user_id, grp ORDER BY streak_days DESC;

How it works: If dates are consecutive (Jan 1, 2, 3), subtracting ROW_NUMBER gives the same "grp" value (Dec 31, Dec 31, Dec 31). Non-consecutive dates produce different groups.

05 Year-over-year growth per product ▼
WITH yearly AS ( SELECT product_id, EXTRACT(YEAR FROM order_date) AS yr, SUM(amount) AS total FROM orders GROUP BY product_id, EXTRACT(YEAR FROM order_date) ) SELECT product_id, yr, total, LAG(total) OVER ( PARTITION BY product_id ORDER BY yr ) AS prev_year, ROUND( (total - LAG(total) OVER ( PARTITION BY product_id ORDER BY yr )) * 100.0 / NULLIF(LAG(total) OVER ( PARTITION BY product_id ORDER BY yr ), 0) , 2) AS yoy_growth_pct FROM yearly;
06 Pivot rows to columns (manual) ▼

Turn rows into columns without a PIVOT keyword:

-- Data: (product, quarter, sales) -- Goal: one row per product, columns = Q1, Q2, Q3, Q4 SELECT product, SUM(CASE WHEN quarter = 'Q1' THEN sales ELSE 0 END) AS q1, SUM(CASE WHEN quarter = 'Q2' THEN sales ELSE 0 END) AS q2, SUM(CASE WHEN quarter = 'Q3' THEN sales ELSE 0 END) AS q3, SUM(CASE WHEN quarter = 'Q4' THEN sales ELSE 0 END) AS q4 FROM quarterly_sales GROUP BY product;

Works on every database. No need for vendor-specific PIVOT syntax.

07 Find employees earning more than their manager ▼
SELECT e.name AS employee, e.salary AS emp_salary, m.name AS manager, m.salary AS mgr_salary FROM employees e JOIN employees m ON e.manager_id = m.id WHERE e.salary > m.salary;

Self-join pattern. Join employees to itself using the manager_id relationship, then filter where employee earns more.

08 Cumulative distribution / running percentage ▼
SELECT product, sales, SUM(sales) OVER (ORDER BY sales DESC) AS cum_sales, ROUND( SUM(sales) OVER (ORDER BY sales DESC) * 100.0 / SUM(sales) OVER () , 2) AS cum_pct FROM product_sales ORDER BY sales DESC;

Useful for Pareto / 80-20 analysis — find which products contribute to 80% of revenue.

24 Conceptual Q&A

01 What is normalization? When would you denormalize? ▼

Normalization: Organizing tables to reduce redundancy. Common forms:

1NF: No repeating groups. Each cell has one value.

2NF: 1NF + no partial dependencies (every non-key column depends on the full primary key).

3NF: 2NF + no transitive dependencies (non-key columns don't depend on other non-key columns).

Denormalize when: Read-heavy workloads (reporting/analytics), reducing expensive JOINs, data warehousing (star/snowflake schemas), or when write frequency is low.

02 ACID properties? ▼

Atomicity: Transaction is all-or-nothing. If any part fails, entire transaction rolls back.

Consistency: Transaction moves DB from one valid state to another. Constraints are always satisfied.

Isolation: Concurrent transactions don't interfere with each other. Each sees a consistent snapshot.

Durability: Once committed, data survives crashes. Written to persistent storage.

03 Primary Key vs Unique Key vs Foreign Key? ▼

Primary Key: Uniquely identifies each row. NOT NULL. One per table. Creates clustered index (SQL Server/MySQL).

Unique Key: Ensures uniqueness. Allows one NULL (varies by DB). Multiple per table.

Foreign Key: References another table's primary/unique key. Enforces referential integrity. Can have NULLs. Can have duplicates.

04 What are views? Materialized views? ▼

View: Saved query — virtual table. No data stored. Re-executes every time you query it. Good for abstraction and access control.

Materialized View: Saved query + cached results on disk. Faster reads but needs manual or scheduled refresh. Good for expensive aggregations in reporting.

-- View: CREATE VIEW active_users AS SELECT * FROM users WHERE status = 'active'; -- Materialized View (Postgres): CREATE MATERIALIZED VIEW monthly_stats AS SELECT month, SUM(sales) FROM orders GROUP BY month; -- Refresh: REFRESH MATERIALIZED VIEW monthly_stats;
05 Stored Procedure vs Function? ▼

Stored Procedure: Can perform actions (INSERT, UPDATE, DELETE). Doesn't need to return a value. Called with EXEC/CALL. Can have output parameters.

Function: Must return a value. Can be used in SELECT/WHERE. Generally no side effects (no DML in most DBs). Called inline in queries.

Interview version: Procedures DO things. Functions COMPUTE things.

06 What is a transaction? Isolation levels? ▼

A transaction is a group of operations treated as one unit. Either all succeed (COMMIT) or all fail (ROLLBACK).

BEGIN TRANSACTION; UPDATE accounts SET balance = balance - 100 WHERE id = 1; UPDATE accounts SET balance = balance + 100 WHERE id = 2; COMMIT;

Isolation Levels (from least to most strict):

READ UNCOMMITTED: Can see uncommitted data (dirty reads). Fastest but riskiest.

READ COMMITTED: Only sees committed data. Default in PostgreSQL, SQL Server, Oracle.

REPEATABLE READ: Same query returns same data within a transaction. Default in MySQL.

SERIALIZABLE: Full isolation — transactions execute as if sequential. Slowest but safest.

07 Star Schema vs Snowflake Schema? ▼

Star Schema: Fact table at center, dimension tables directly connected. Denormalized dimensions. Fewer JOINs. Faster reads. Simpler queries.

Snowflake Schema: Same as star but dimensions are normalized (split into sub-dimensions). More JOINs. Saves storage. More complex queries.

In practice: Star schema is preferred for analytics / data warehousing. The storage savings from snowflake rarely justify the query complexity.

08 What are window frames? ROWS vs RANGE vs GROUPS? ▼

ROWS: Physical row count. ROWS BETWEEN 2 PRECEDING AND CURRENT ROW = exactly 3 rows.

RANGE: Logical value range. Includes all rows with the same ORDER BY value (ties). Default behavior.

GROUPS: Like RANGE but counts distinct groups. GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW = current group + 1 preceding group of distinct values. (Postgres 11+, SQLite.)

Interview takeaway: If you want a strict running total with no tie-related surprises, always specify ROWS explicitly.

25 Golden Rules

⚡ 10 Things to Remember Walking Into an SQL Interview

  • NULL is not a value — it's unknown. NULL = NULL is not TRUE. Use IS NULL.
  • WHERE runs before GROUP BY — you can't filter aggregates with WHERE. Use HAVING.
  • Window functions can't go in WHERE — wrap in CTE or subquery first.
  • COUNT(*) counts NULLs, COUNT(col) doesn't — know which you need.
  • JOINs can multiply rows — one-to-many produces duplicates. Aggregate before or after, not both.
  • NOT IN with NULLs returns empty — use NOT EXISTS or filter NULLs.
  • Default window frame includes ties — specify ROWS for exact behavior.
  • CTEs are for readability, not performance — they're usually inlined by the optimizer.
  • Functions on columns kill indexes — WHERE YEAR(col) = 2026 = full scan.
  • Always state your SQL dialect — syntax varies across databases. Interviewers appreciate precision.
